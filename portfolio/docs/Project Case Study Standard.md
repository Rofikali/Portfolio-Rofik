# Project Case Study Standard — Portfolio-Rofik

A case study must be truthful about **the status of the linked project**, not merely present an impressive architecture diagram. The portfolio hosts project descriptions but does not itself run the case-study applications. See [content policy](content-seo-accessibility.md) and [evidence register](status-and-evidence.md).

## Required narrative (use judgment)

1. **Problem and audience:** who needs what, and why?
2. **Scope and status:** implemented, recorded-verified, partial, planned, illustrative or historical; attach date and source/commit.
3. **Requirements and constraints:** correctness, accessibility, safety, performance, budget and operating limits.
4. **HLD/LLD when relevant:** component boundaries, data flows, contracts; distinguish actual from conceptual.
5. **Technology and patterns:** explain tradeoffs and alternatives, not a language badge list.
6. **Security, privacy and testing:** threats, mitigations, evidence, unresolved risks, and the exact environment/SHA.
7. **Measured outcomes:** user impact, benchmarks or costs only if reproducible; otherwise say **not measured**.
8. **Tradeoffs/lessons:** what failed or remains blocked; clearly label future work and linked PRs.

**Optional, not mandatory:** database schema, API definitions, queues, Rust/C FFI, algorithm complexity or infrastructure diagrams **only when the featured project actually uses or plans them**. A static Vue gallery should not invent a data layer. Use [case-study template](templates/case-study-template.md) as a writing aid, not source evidence.

**Publishing review:** owner verifies clients/employment dates, personal data, screenshots, license claims, demos and links before changing live portfolio content.
